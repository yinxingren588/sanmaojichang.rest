不同主张需要不同证据。“采用专线”“某次测速很快”“能打开某个平台”和“长期稳定”不能互相替代。读资料时先问：这句话描述什么条件，证据能覆盖到哪里？

## 线路名称描述的是哪一段

IPLC、IEPL 等标签需要说明具体覆盖的线路段、接入和出口。即便某一段采用特定线路产品，最终体验仍与本地接入、服务器负载和远端应用有关。

没有端到端记录时，可以写“服务商说明使用某类线路”，不能直接写“所以一定稳定”。基础概念见[IPLC 与 IEPL](/glossary/iplc-iepl/)。

## 单次测速能回答什么

它最多回答：在注明的时间、设备、网络和目标下，这一次观测到了什么。没有说明环境的图片，很难复现，也无法公平比较品牌。

延迟、吞吐与波动是不同指标。某次下载速度高，不代表握手快；一次握手快，也不代表高峰期持续传输稳定。原始记录比醒目的大数字更有价值，解释见[延迟与速度](/glossary/latency/)。

## 稳定性需要重复观察

连续记录应覆盖不同日期和时段，尤其是你真正使用的时间。记录成功、失败、恢复时间和测试条件，区分本地网络中断与服务端异常，不要只保留成功样本。

本站稳定性榜要求至少七天、每天至少三次并包含晚高峰的记录。这是本站设定的准入规则，不代表某个通用行业认证。环境不一致的结果也不能直接混排。

## AI 与流媒体可访问性

能打开首页与能完成实际任务，是两种不同证据。账号地区、订阅等级、平台支持范围和支付方式可能影响结果；同一平台的网页、移动应用和 API 也可能有不同条件。

应明确测试了什么功能、哪个地区和何时测试。不应从一次成功推导“永久解锁”“所有账号可用”，也不应把服务商的支持列表写成本站亲测。

## 一份证据最少应包含什么

| 主张 | 最低应查看的材料 |
| --- | --- |
| 价格与流量 | 当前套餐页、周期、单位、倍率和核验日期 |
| 线路类型 | 原始说明、覆盖范围与尚未披露的部分 |
| 实际体验 | 设备、网络、时段、目标、方法与结果 |
| 稳定性 | 连续样本、失败记录及环境一致性 |
| 支持情况 | 对应功能与账号条件，以及测试日期 |

## 遇到未知就停在未知

没有资料不等于表现不好，也不等于可以放心假定。信息不足时，最合理的结论往往是“尚未核实”，等待更多证据。你可以按[试用清单](/blog/trial-checklist/)建立自己的记录，再结合[稳定优先专题](/recommend/stable/)作判断。
